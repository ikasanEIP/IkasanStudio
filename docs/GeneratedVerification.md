# Generated verification baselines

**Tools → Ikasan Studio → Generate/Refresh Verification Tests…**, also available on the
module's canvas context menu, creates Studio-owned tests in `generated/src/test/java/org/ikasan/studio/verification`.
Baseline metadata and instructions live in `generated/src/test/resources/studio-verification`.
The existing `generated` Maven module runs them; no additional module is needed. Commit the
tests, updated `generated/pom.xml` and baseline metadata; `target/` is ordinary Maven output. Tests contain no TODOs or developer enablement flags.

## Initial coverage

This first increment checks, per flow:

- the public flow factory's return contract;
- component factory signatures where the meta-pack declares factory generation;
- concrete user implementation classes against declared interfaces.

These tests check structure and interface compatibility. They do not start Spring, verify wiring
at runtime, send input or check delivery, routing, exclusions or business results. Add those
scenarios in developer-maintained `user-flow-tests`; their coverage depends on the scenarios
implemented. A successful build proves the structural checks only. Maven compilation and
reflective linkage failures are real failures. Results contain only the checks performed,
without a permanently skipped runtime placeholder.

Checks are generated by version-specific FTL templates for V3.3.9 and V4.1.6. Factory availability
comes from existing metadata. `verificationImplementationContract` can override the user-class
contract when it differs from the public component interface, such as Default Message Filter's
`FilterRule`. No custom-component behaviour is inferred.

## Running and refreshing

Run from the project root:

```sh
mvn -pl generated -am test
```

Use normal IntelliJ JUnit/Maven controls as well. Reports are in
`generated/target/surefire-reports`, including failure and skipped-check reasons.
Generation does not run tests. Running tests does not regenerate them.

Under `generated/src/test/resources/studio-verification`, `baseline-model.json` records the original model; `baseline.properties` records its SHA-256,
pack ID and baseline format. `BASELINE_MODEL_SHA256` in `GeneratedVerificationSupport` stores
the same hash: the UTF-8 bytes of the saved `model.json` when the tests were generated. It is
not a hash of Java source files or compiled classes, and cannot detect source-only edits.
Running tests or migrating does not update it; explicit test regeneration does. At test startup, a differing model fingerprint prints a warning,
but assertions stay unchanged. Formatting-only model changes also affect this fingerprint.
There is no editor stale-status indicator in this first increment.

Refreshing requires explicit confirmation and archives the entire previous `generated/src/test` tree to
`generated/src/test.bak<timestamp>-<unique-id>` before replacing Studio’s verification package and metadata. Unrelated tests remain in place. Temporary developer
corrections are preserved in that archive. Generation adds `/generated/src/test.bak*/` to the
project root `.gitignore` so these backups and their contents stay out of version control. No checksum-based merging is attempted. Generation
refuses to replace sources changed after the confirmation snapshot.

## Before and after migration

1. Generate the baseline and run it on the original application.
2. Save the Surefire reports outside `target/`, which subsequent runs can replace.
3. Upgrade the application. Ordinary Studio generation/migration preserves these test sources and resources.
4. Run the same tests and compare the saved reports. A changed model warning is expected.
5. Only after comparison, optionally refresh the generated baseline.

This initial workflow does not automatically collect or compare before/after reports, and does
not adapt tests across interface changes. A frozen test that cannot compile or link after migration
needs review; refreshing it first would discard that comparison evidence. Business scenarios stay
in the developer-owned [flow tests](IkasanFlowTesting.md).

## Earlier standalone baselines

Generating tests now removes the old `generated-verification` entry from the root Maven reactor,
but retains that directory unchanged as evidence. Review or copy any temporary corrections
before generating a new baseline. Once the new baseline is accepted, the old directory may
be archived or removed explicitly. Do not relocate or refresh tests between migration runs.
